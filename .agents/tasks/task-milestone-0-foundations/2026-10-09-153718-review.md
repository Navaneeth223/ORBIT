# Milestone 0 foundations

Monorepo structure established with pnpm workspaces and Turborepo orchestration. Six packages created: two applications (Vite React PWA web frontend, Fastify TypeScript API backend) and four shared packages (types/schemas, placeholder content, placeholder game engine, shared tooling configs). All build pipelines, code quality tools, Git hooks, CI workflow, Docker development environment, and documentation in place.

**Watch for:** Nothing blocking. The foundation is solid and all acceptance criteria are met. Docker services defined but not running in verification environment (expected, not a codebase issue).

**Verdict**: APPROVED

---

## High-level view

The monorepo structure correctly implements workspace dependency management with pnpm and caching with Turborepo. Design tokens define a dark-first theme with light mode overrides and brand colors for both partners (Navi purple #7c6af7, Raya pink #f76aac). The API validates environment variables with Zod on startup and redacts JWT secrets from Pino logs. i18n infrastructure supports English and Thai from day one, with Thai translations flagged for user review. Conventional Commits are enforced via commitlint, and lint-staged runs ESLint and Prettier on pre-commit. The health endpoint validates responses with a shared Zod schema between client and server, demonstrating cross-package type safety. Docker Compose defines MongoDB, Redis, and MailHog with health checks and persistent volumes. GitHub Actions CI pipeline covers install, lint, type-check, test, and build for the entire monorepo.

## Workspace dependency graph

The monorepo uses pnpm workspaces with the `workspace:*` protocol for internal dependencies. Only `@orbit/shared` is consumed by other packages at this stage: both `apps/web` and `apps/api` import it for constants, types, and the `HealthResponseSchema`. This demonstrates that the monorepo wiring works correctly—TypeScript resolves cross-package imports, type declarations are generated, and Turborepo's dependency graph ensures `@orbit/shared` builds before its dependents.

The two placeholder packages (`@orbit/content` and `@orbit/game-engine`) export stub constants and are not yet consumed by other packages. This is intentional; they exist to prove the monorepo structure and will be populated in later milestones.

Turborepo pipelines define task dependencies: `test` depends on `build`, `type-check` depends on `^build` (transitive dependencies). Caching works as verified—build outputs are reused across invocations, and the verification evidence shows 4 of 5 lint tasks and 5 of 6 type-check tasks served from cache during repeated runs.

## Design system and theming

The design tokens in `apps/web/src/styles/tokens.css` define a complete color palette, typography scale, spacing system, border radii, shadows, and animation timing. Dark theme is the default; light theme overrides are applied via `@media (prefers-color-scheme: light)`. Brand colors for the two partners are distinct: Navi's purple (#7c6af7) and Raya's pink (#f76aac). Semantic colors (success green, warning yellow, error red, info blue) are defined for UI feedback.

Typography uses a system font stack with a serif display fallback. Font sizes range from `--font-size-xs` (12px) to `--font-size-3xl` (30px). Spacing tokens follow a geometric scale (4px, 8px, 16px, 24px, 32px, 48px). Border radii cover common use cases from sharp (`--radius-sm`: 4px) to pill-shaped (`--radius-full`: 9999px).

Tailwind CSS is configured to consume these tokens, allowing utility classes like `bg-[--color-bg]` or direct `var(--color-navi)` references in custom CSS. This approach gives the flexibility of utility-first styling with centralized theme control. The light theme shadows are lighter (lower alpha) than the dark theme shadows, which is correct—dark mode needs heavier shadows for elevation contrast.

## Internationalization infrastructure

i18next is configured with two locales: English (`en`) and Thai (`th`). Language detection reads from localStorage key `orbit-lang`, falls back to browser language, and defaults to English if neither is set. Translation files are JSON with nested keys: `app.name`, `app.tagline`, `splash.loading`, `nav.home`.

The Thai translation file includes `_meta.reviewed: false`, signaling that Thai strings need review by Raya. This is a pattern for tracking translation quality. The splash page uses `useTranslation` to display the app name and tagline, proving the i18n wiring works. However, no UI component exists to switch languages. A user can change languages only by setting `localStorage.setItem('orbit-lang', 'th')` and reloading. This may be intentional for Milestone 0 (infrastructure only) or may be an oversight; either way, it's not blocking—the infrastructure is ready, and a language switcher component can be added in a later milestone.

## Environment validation and secret redaction

The API validates all environment variables on startup using a Zod schema in `apps/api/src/config/env.ts`. Required variables include `PUBLIC_WEB_ORIGIN`, `MONGODB_URI`, `REDIS_URL`, three JWT/cookie secrets (each must be at least 32 characters), and `MAX_USERS` (default 2). If validation fails, the process exits with a formatted error message, preventing the server from starting in a misconfigured state.

Pino logger redacts six paths: `config.jwtAccessSecret`, `config.jwtRefreshSecret`, `config.cookieSecret`, and their uppercase env var equivalents. The redaction removes values rather than masking them (`remove: true`), so logs never contain secret material even in redacted form. In development, Pino uses `pino-pretty` for human-readable colored logs; in production, it outputs newline-delimited JSON for structured log aggregation.

The verification evidence confirms secrets are not logged. This pattern is critical for a two-person app where both users have access to logs during development but should never see each other's credentials or see secrets leak into monitoring systems.

## Health endpoint and shared schema validation

The API health endpoint at `GET /health` returns `{ status: 'ok', timestamp: ISO8601, version: string }`. The response is validated server-side with `HealthResponseSchema.parse()` from `@orbit/shared`. The web app's health check page fetches this endpoint and parses the response with the same schema. This demonstrates cross-package type safety: if the API changes the response shape without updating the schema, TypeScript compilation fails. If the API returns malformed data at runtime, Zod validation throws an error with a detailed message.

The schema uses `z.literal('ok')` for the status field, which is stricter than `z.string()`—the response can only ever be `{ status: 'ok' }`, not `{ status: 'healthy' }` or any other variant. This makes failure states explicit: if the server is unhealthy, it should return a different status code or a different endpoint, not a different value in the same field.

The health endpoint is tested in `apps/api/src/__tests__/health.test.ts` with a real Fastify instance, not a mock. This verifies route registration, handler logic, and response validation end to end.

## Git hooks and commit enforcement

Husky hooks are installed in `.husky/`: `pre-commit` runs `lint-staged`, which formats and lints only staged files, and `commit-msg` runs `commitlint` to enforce Conventional Commits. The configuration allows seven types: `feat`, `fix`, `chore`, `docs`, `test`, `refactor`, `style`. Commit messages must match the format `type(optional-scope): description`.

Lint-staged applies ESLint and Prettier to TypeScript files and Prettier alone to JSON, Markdown, and YAML files. This prevents broken code or misformatted files from entering the repository. The hooks work on Windows (verified in FEAT-001 findings), which required no special configuration—Husky 8+ handles cross-platform execution automatically.

The verification evidence does not include a test commit, but the hooks are installed and executable, and the configuration files are syntactically correct. The risk of hooks failing in actual use is low.

## Docker development environment

`docker-compose.yml` defines three services: MongoDB 7, Redis 7 Alpine, and MailHog. Each service has a health check: MongoDB uses `mongosh --eval "db.adminCommand('ping')"`, Redis uses `redis-cli ping`, and MailHog uses `wget --spider http://localhost:8025`. Volumes are named (`orbit-mongo-data`, `orbit-redis-data`) and use the local driver for persistence.

MongoDB is configured with `MONGO_INITDB_DATABASE: orbit`, which creates the database on first run. Redis runs with `--appendonly yes` for persistence. MailHog exposes two ports: 1025 for SMTP (API will send emails here) and 8025 for the web UI (humans can inspect captured emails).

Health checks include retry counts and start periods to handle slow container startup. The compose file is version 3.8, which is compatible with Docker Compose 1.25+ and Docker Engine 19.03+.

The verification evidence notes that Docker is not available in the verification environment, so services were not started. The API uses MongoDB (verified running locally on Windows in FEAT-005 findings), but Redis and MailHog require Docker. This does not block Milestone 0 approval—the compose file is correct, and services will start when Docker is installed.

## GitHub Actions CI pipeline

The workflow in `.github/workflows/ci.yml` runs on push or pull request to `main`. It checks out the repository, sets up Node 20 and pnpm 8, caches the pnpm store, installs dependencies with `--frozen-lockfile`, and runs four commands: `pnpm lint`, `pnpm type-check`, `pnpm test`, `pnpm build`.

The pnpm cache uses the hash of `pnpm-lock.yaml` as the key, so the cache is invalidated only when dependencies change. This speeds up CI runs. The workflow uses `actions/checkout@v4`, `actions/setup-node@v4`, `pnpm/action-setup@v2`, and `actions/cache@v3`, all of which are current stable versions.

The workflow does not include environment variable setup, which means it cannot start the API server (MongoDB and Redis are not available in CI). This is acceptable for Milestone 0—builds and unit tests run without external services, and integration tests will be added in later milestones. If integration tests are added, the workflow will need a `services` block for MongoDB and Redis or a separate job that uses Docker Compose.

## Placeholder packages readiness

`@orbit/content` exports a single constant (`CONTENT_PACKAGE_VERSION`) and has two passing tests. The package README explains that future content (daily questions, stationery, companion species) will live here as versioned, schema-validated, localized JSON. The package is importable and builds cleanly, proving the monorepo structure works for packages that will be populated later.

`@orbit/game-engine` exports a stub `GameEngine` interface and has five passing tests (confirmed in verification evidence). The README documents design principles: pure functions, injectable clock (never `Date.now()`), no side effects, all game logic testable in isolation. The tests include a demonstration of the injectable clock pattern, which is critical for time-based game mechanics (reveal gating, daily resets, streak calculations). This shows the implementer understands the requirement and has established the testing pattern for future logic.

Both placeholder packages satisfy their acceptance criteria: they build, test, and document intent. They contribute no behavioral value yet, but they prove the monorepo structure scales to additional packages.

## Test coverage baseline

The verification evidence reports 18 tests passing across five packages: 8 in `@orbit/shared` (constants and health schema validation), 5 in `@orbit/game-engine` (injectable clock and stub logic), 2 in `@orbit/content` (package loading), 2 in `@orbit/web` (React smoke test), and 1 in `@orbit/api` (health endpoint). This is a smoke-test baseline, not comprehensive coverage.

The shared package tests cover both valid and invalid inputs for `HealthResponseSchema`, which is good—Zod schemas should always be tested with malformed data to verify they reject it. The API test uses a real Fastify instance, which is better than mocking. The web test uses React Testing Library, which is the recommended approach for React component testing.

No e2e tests exist yet, which is expected for Milestone 0. The ORBIT master prompt specifies that e2e tests are not required until later milestones. The current test suite is sufficient to catch regressions in core logic and API contracts.
